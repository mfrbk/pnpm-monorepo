# Vite 双引擎架构与底层原理

> [← 返回总纲](./README.md) · 本系列第 1 篇:开发为何"原生 ESM + esbuild 预构建"、生产为何"Rollup 打包",以及 HMR 为何近乎瞬时

几乎所有"Vite 为什么这么快"的问题,都指向同一个**架构总开关**:Vite **开发环境几乎不做打包,生产环境却老老实实打包**,而且两个阶段用的是**两套引擎**。不理解这个开关,你看 Vite 的每个配置都会困惑;理解了它,Vite 的行为就自洽了。

## 一、总开关:开发"能不打包就不打包",生产"必须打包"

先记住一张对照图,它是全系列的锚点:

|          | 开发模式(dev)                     | 生产模式(build)                     |
| -------- | --------------------------------- | ----------------------------------- |
| 目标     | **让浏览器最快跑起来**,压缩工作量 | **产出最优文件**,压缩体积/请求数    |
| 处理源码 | **按需转译单文件**,不做全量打包   | 全量打包成少量 chunk                |
| 依赖处理 | esbuild **预构建**成 ESM 缓存     | 与业务代码一起打包进产物            |
| 打包引擎 | 基本没有(浏览器就是"打包器")      | **Rollup**(未来 Rolldown)           |
| 交付形态 | 每个模块是独立文件请求            | 几个(或几十个)经过摇树/压缩的 chunk |

**为什么要分裂成两套?** 因为 dev 与 prod 的诉求根本冲突:开发要"**改一行代码→1 秒内看到**",生产要"**文件最小、请求最少、缓存最优**"。没有一个单一模式能同时极致满足两者,于是 Vite 干脆**各自用最合适的引擎**,代价是两条流水线偶有不一致(下面第四节会讲它的解法方向)。

```
开发:  index.html → <script type="module"> → 浏览器按需 import → Vite 逐个转译 → 原生 ESM 直接执行
生产:  index.html + src → Rollup 全量打包(摇树/分割/压缩) → 少量 chunk → 浏览器加载
```

## 二、开发引擎:原生 ESM + esbuild 预构建

### 1. 原生 ESM:让浏览器替你"遍历依赖图"

Webpack 开发的典型路径是:**从入口出发,把整棵依赖图打包好,浏览器才收到第一行可执行 JS**——于是冷启动时间与项目规模强相关,项目越大越慢。

Vite 反其道而行:**开发服务器启动后几乎什么都不做**,真正干活的是浏览器自己。`index.html` 里的入口长这样:

```html
<!-- Vite 把 index.html 当作入口;真正启动应用的是这行标签 -->
<script type="module" src="/src/main.js"></script>
```

浏览器解析到它,会**原生地**发起 `GET /src/main.js`;Vite 只把这个文件做轻量转译后返回;浏览器执行它时看到 `import './foo.js'`,又会**原生地**去请求 `foo.js`……依赖图是**浏览器在运行时按需铺开的**:

```
浏览器: 请求 main.js
Vite:   转译 main.js 返回(import 已改写成可解析的 URL)
浏览器: 执行 → 发现 import './App.vue' → 再请求
Vite:   转译 App.vue(交给插件)→ 返回
浏览器: ……继续往下,用到谁才请求谁
```

- **Vite 只转译"被浏览器真正请求到的模块"**,而不是预编译整个项目 → 冷启动与代码规模几乎脱钩;
- 每个转译结果都带内容哈希做缓存,浏览器可 `304` 复用,**二次访问(刷新)极快**;
- 代价也很明显:**浏览器每次 import 就是一次 HTTP 请求**,模块一多请求数爆炸——这正是 dev 能忍、prod 不能忍,以及**依赖必须预构建**的原因之一。

> 一句话:Webpack dev 是"**先建好整张图再给你**",Vite dev 是"**你走到哪,我画到哪**"。

### 2. bare imports(裸模块导入)与 esbuild 预构建

**裸模块导入**指 `import React from 'react'` 这类不带路径、直接写包名的写法。浏览器原生不认识——它没法去 `node_modules` 里自己找。而 Vite 又不能在 dev 给每个源文件都做依赖解析,于是祭出 **依赖预构建(dependency pre-bundling)**:冷启动时用 **esbuild** 把项目依赖**预先打包成浏览器可用的 ESM**。

具体来说,预构建一口气解决三个问题:

| 问题                                                                            | 预构建的做法                                                                                            |
| ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| ① 裸模块导入浏览器无法解析                                                      | 把 `'react'` 解析到真实文件,并 rewrite 成带版本 hash 的 URL:`/node_modules/.vite/deps/react.js?v=8f9a…` |
| ② 大量依赖是 **CJS / UMD**(内部用 `require`,浏览器 ESM 无法直接用,HMR 也不兼容) | 用 esbuild **转成标准 ESM**                                                                             |
| ③ 一个依赖内部动辄上百个文件 → 若原样 serve,浏览器要发上百个请求                | esbuild **合并**成更少的模块,大幅减少请求                                                               |

产物落在 **`node_modules/.vite/deps/`**,文件名带版本 hash,浏览器可强缓存。流程与缓存策略:

```
冷启动:esbuild 扫描依赖(哪些裸导入)→ 预构建 → 写入 .vite/deps
   │
   ├─ 缓存依据:lockfile(pnpm-lock / package-lock)+ 相关配置的内容 hash
   │    依赖没变 → 二次冷启动直接复用,几乎秒起
   └─ 依赖变了(新增/升级包)→ 自动重新预构建并刷新页面
```

**为什么要用 esbuild?** 因为"即便只是预构建依赖",全量重扫也是启动成本的大头。esbuild 用 **Go** 编写,转译/打包速度比传统 JS 实现快一到两个数量级,把冷启动压到可接受范围;Vite 再靠缓存让**二次启动更快**。可配置项收敛在 `optimizeDeps`(`include` / `exclude` / `esbuildOptions`),按需微调即可。

> 理解这点后,很多怪现象有了答案:**首次 `npm run dev` 慢**(在做预构建)、**`npm install` 后偶尔要求重启 dev**(依赖清单变了)、**直接改 `node_modules` 里的代码不生效**(预构建缓存管着)。

### 3. 源码按需转译:每份都"轻"

对 `node_modules` 走预构建,对**业务源码**则**不做预编译**:Vite server 收到请求时,才针对该文件类型调用对应插件做一次**单文件 transform**(TS 去类型、`.vue` 编译、`.scss` 转 CSS),然后返回。源码永远保持"一个文件一个模块"的形态在浏览器里跑。

## 三、HMR:为什么"几乎瞬时"

如果说"不打包"换来的是**冷启动快**,那 HMR 的"瞬时"则来自**同样的单模块粒度**:

- 你保存文件,dev server 的 watcher 立刻只**让这一个模块(及其 importers 链)失效**;
- 通过 WebSocket 推送一条**精确的更新指令**(哪个模块变了、用什么时间戳重新取),浏览器 HMR 客户端重新请求**这一个模块的新版本**;
- 由 accept 边界决定是**局部热替换还是整页刷新兜底**——机制与 Webpack 的冒泡一致(可对照 [Webpack HMR 专题](../webpack/hmr.md))。

```
改动 App.vue → watcher → WS 推 { type: 'update', path: '/src/App.vue', ts }
   → 浏览器用带时间戳的 URL 重新拉取该模块 → import.meta.hot 边界应用
      ├─ 被框架插件 accept(React Fast Refresh / Vue) → 局部热更,状态保留 ✅
      └─ 无人 accept → 整页 reload 兜底
```

**为什么比 Webpack 快一个量级?** 关键在"**要重新做的工作**"不同:Webpack 每次改动都要让**编译器**再走一遍(即便增量、即便有缓存,图的规模仍影响单次编译);而 Vite 在开发期**根本没有"打包"这一步**——改一个文件,server 只需转译并返回那一个文件,耗时与项目规模几乎无关,所以单次热更稳定在毫秒级。

CSS 更新甚至更简单:改动样式 → 推 `css-update`,浏览器直接替换 `<style>` 内容,不走模块 JS 逻辑,天然瞬时。

> 对照阅读:热更新的 accept 冒泡、dispose 清理、`module.hot` 对应 Vite 的 `import.meta.hot`,心智模型完全同源,只是 Webpack 在"编译器内热补丁",Vite 在"浏览器原生的模块图里换文件"。

## 四、生产引擎:为什么"还要"打包(Rollup,未来 Rolldown)

### 1. 未打包的 ESM 上线,代价难以接受

| 代价             | 说明                                                                                    |
| ---------------- | --------------------------------------------------------------------------------------- |
| **请求爆炸**     | 每个 import 一次请求;应用几百个模块 → 首屏几百个请求,即使 HTTP/2 也远不如几十个文件高效 |
| **没有全局优化** | 浏览器不会为你的模块图做**摇树、代码分割、压缩**——这些必须构建期静态分析后完成          |
| **缓存与长尾**   | 没有 contenthash 式产物,升级部署难以精准失效缓存                                        |
| **兼容性**       | 裸模块导入语法、部分浏览器对 ESM 的支持,都需要降级/垫片                                 |

所以上线前 **Rollup 把模块图打包成少量 chunk**,并完成摇树、代码分割、异步块、压缩、资源哈希——对产物尺寸与加载体验负责。**开发交给"最轻的转译",生产交给"最优的打包",各取所长**,这正是双引擎的完整逻辑。

### 2. 为什么生产选 Rollup,而不是继续用 esbuild

esbuild 转译/打包很快,但它作为"产物级打包器"的深度优化不如 Rollup:**摇树更精细、代码分割与产物可控性、庞大的插件生态**,都是 Rollup 的强项。Vite 的取舍是:**生产产物追求"品质"(体积/结构),构建速度其次**(构建本身也可用 esbuild 做 JS/CSS 压缩,追求更狠的压缩可换 terser)。这个判断也解释了为何 Vite 的插件接口直接兼容 Rollup——见 [插件篇](./plugins.md)。

### 3. 未来方向:Rolldown,统一两条流水线

双引擎有一个天然隐患:**dev(esbuild 转译)与 prod(Rollup 打包)的语义偶有差异**,某些代码 dev 正常、prod 报错或反之。Vite 正在用 **Rust 编写的 Rolldown**(基于 oxc)逐步统一两条流水线——用同一个引擎承担 dev 转译与 prod 打包,既消除行为分裂,又带来更快的生产构建。

**当下要建立的认知**:

- Rolldown 是**演进方向**,尚未成为默认;本系列所有"心智"部分(按需 dev / 打包 prod / 摇树 / 分割 / HMR)不会因引擎替换而失效;
- 判断资料新旧的方法:看到"Vite 用 esbuild 预构建 / 用 Rollup 打包"属于**现状**,看到"Rolldown 统一"属于**路线图**,别把两者当成同一时点的实情。

## 速查

| 主题             | 一句话记住                                                                |
| ---------------- | ------------------------------------------------------------------------- |
| 总开关           | dev 尽量不打包(浏览器按需 import),prod 必须打包(Rollup 优化产物)          |
| 原生 ESM         | 浏览器自己铺依赖图,Vite 只转译被请求到的模块 → 冷启动与规模脱钩           |
| 预构建           | esbuild 把依赖转成 ESM 并缓存进 `.vite/deps`,解决裸导入/CJS 转换/请求爆炸 |
| HMR              | 改一个文件只重取那一个模块,与项目规模几乎无关 → 毫秒级                    |
| 为何 prod 要打包 | 请求数、摇树、分割、压缩、缓存这些全局优化只能构建期做                    |
| 为何选 Rollup    | 产物品质与插件生态;esbuild 只在 dev/压缩场景发挥速度                      |
| Rolldown         | Rust 统一 dev/prod 的未来方向;当前心智不变                                |
