# React Hooks 与并发调度原理

> [← 返回主 README](../README.md) · React 原理学习笔记:Hooks 链表 / 闭包机制,以及并发调度四阶段

类组件把状态"寄存在实例"上;函数组件没有实例,每次调用都是一次全新执行。React 靠**闭包 + 链表**让函数组件也能"记住"状态,让 UI 纯粹由状态驱动;**调度系统**则回答状态变化后"何时算、算什么、何时上屏"。全文两大块:**Hooks 的底层机制与常用 Hook 原理**、**React 并发调度的完整流程**。

## 一、Hooks 的底层机制

函数组件没有实例,那每次调用时 Hook 状态存在哪、靠什么找回上一次的值?两条底层机制:**Fiber 上的单向链表**负责存,**渲染快照与闭包**负责取。

### 存储:Fiber 上的单向链表

每个函数组件都对应一个 Fiber 节点,组件内所有 Hook 的状态以**单向链表**挂在节点的 `memoizedState` 属性上:

- 每个链表节点 ≈ `{ memoizedState: 当前状态, queue: 更新队列, next: 下一个 Hook }`。
- React **按调用顺序**遍历链表,把每次 Hook 调用定位到对应的状态节点。因此 Hooks 不能写在条件、循环或嵌套函数里——顺序一旦错乱,链表随之错位,状态就会串到错误的 Hook 上。
- 判别准则:每次渲染是否都以相同顺序、相同次数调用。编码期由 `eslint-plugin-react-hooks` 的 `rules-of-hooks` 规则兜底。

### 执行:渲染快照与闭包

- 组件每次执行都是一次全新函数调用,生成独立的**执行上下文(渲染快照)**,里面的 props / state 都是"渲染当时"的值。
- Hook 通过**闭包**捕获快照中的变量:事件回调、effect 内读到的永远是这次快照的值。
- **依赖数组 deps 控制闭包的生命周期**:每次渲染用 `Object.is` 对新旧 deps 做浅比较。
  - 有变化 → 丢弃旧闭包、重建一个捕获最新值的闭包(useEffect 重跑、useMemo / useCallback 重算);
  - 无变化 → 沿用旧闭包(缓存命中)。
- deps 漏项或过期,闭包就不会重建,回调永远拿着旧值——即**陈旧闭包(Stale Closure)**:

```jsx
function Timer() {
  const [count, setCount] = useState(0)
  useEffect(() => {
    // 空 deps:闭包被"冻结",count 恒为首次渲染的 0
    const id = setInterval(() => setCount(count + 1), 1000)
    return () => clearInterval(id)
  }, [])
  return <div>{count}</div> // 永远停在 1
}
```

修正二选一:把依赖补全 `[count]`(每次变化重启定时器),或用**函数式更新** `setCount(c => c + 1)` 读取最新值;漏依赖问题常由 `exhaustive-deps` 规则提示。

## 二、常用 Hooks 与原理

把底层机制套用到具体 Hook 上,按使用场景分为四类:**状态与上下文、副作用、性能优化、引用**。

### 状态与上下文

管理"组件数据从哪来、怎么变":`useState` / `useReducer` 声明内部状态,`useContext` 跨层级读取共享数据。

#### useState

声明组件状态。首次渲染把初始值写入该 Hook 的 `memoizedState`,并为其建一个**环形更新队列**;调用更新函数时,把 `Update` 对象追加进队列并触发一次调度。要点:

- 传函数做初始值 → **惰性初始化**,仅首次渲染执行一次,避免昂贵计算被反复求值。
- 更新值与旧值 `Object.is` 相同 → React 直接跳过本次更新(bail out)。
- 想拿最新值 / 连续更新,用函数式写法 `setCount(c => c + 1)`。

#### useReducer

处理含多子值或复杂流转逻辑的状态。结构与 useState 相同,只是更新队列里存的是 `action`,触发时调用开发者传入的 reducer:`(state, action) => newState`。**useState 本质是 useReducer 的特例**(内置一个直接覆盖值的 reducer)。

#### useContext

跨层级读取祖先 Provider 的 value,规避 Props Drilling。组件内部建立对该 Context 的**订阅**,value 变化即触发所有订阅组件重渲染。优化:value 通常要用 `useMemo` 缓存,否则父组件每次渲染都产生新 value,连带全部订阅者无谓重渲染。

### 副作用

负责组件与"外部世界"的同步(取数、订阅、手动改 DOM),由两个执行时机不同的 Effect 承接。

#### useEffect

处理与外部系统同步的副作用(取数、订阅、手动改 DOM)。副作用函数与 deps 存入 Hook 节点,**浏览器完成绘制后异步执行**;deps 浅比较决定是否重跑;返回的清理函数在"下一次执行前"与"卸载时"调用,防内存泄漏。deps 语义:

| 写法      | 执行时机                         |
| --------- | -------------------------------- |
| 省略 deps | 每次渲染提交后执行               |
| `[]`      | 仅挂载后执行一次(卸载前执行清理) |
| `[a, b]`  | 任一依赖变化时执行               |

开发环境 StrictMode 会让 effect **双执行一次**,用于暴露未正确清理的副作用(生产不受影响)。

#### useLayoutEffect

在浏览器重新绘制**前**同步执行,用于读取 / 同步修改布局,避免闪烁。结构与 useEffect 相同,只是执行时机提前到 Commit 阶段的 Layout 环节,会**阻塞绘制**。经验法则:能 useEffect 就不用 useLayoutEffect;仅当需要在绘制前同步量到 DOM 尺寸或修好布局、否则会闪一帧时才用它。

### 性能优化

用"缓存"跳过重复计算与无意义的重复渲染。

#### useMemo

缓存昂贵的计算结果。Hook 中同时存"计算结果 + deps",渲染时浅比较,依赖未变直接返回缓存值,变了才重跑工厂函数并更新缓存。

#### useCallback

缓存函数实例,避免子组件因拿到新函数引用而无效重渲染。实现上等价于"把函数包进 useMemo",只是缓存对象是函数本身:依赖不变则返回**同一份引用**,保持引用稳定。

> 二者都是"命中缓存"的性能优化,**不是语义保证**——React 可以随时丢弃缓存。引用不稳应首先反思组件结构(状态上提、拆分、稳定 props),而不是靠 memo 硬扛。

### 引用

保存"需要跨渲染存活、但改动不该触发渲染"的可变数据。

#### useRef

获取 DOM 引用,或保存"需要跨渲染存活、但改动不该触发重渲染"的可变数据。返回普通对象 `{ current: initialValue }`,它不进状态更新队列,改 `.current` **不会触发重渲染**。由于闭包捕获的是 ref **对象**而非值,`ref.current` 能穿透渲染快照、实时读到最新数据——常用于定时器、事件回调里读取最新 state。

## 三、React 并发调度:四阶段

同步渲染整棵 diff 会长时间占用主线程、卡顿掉帧。React 拆成两件事来解决:**Scheduler 决定"什么时候算",Fiber 决定"算什么"**。一次更新依次走完四个阶段:

```
① 触发更新 + Lanes 定级
        ↓
② Scheduler 排队 + 时间切片(~5ms,让出主线程)
        ↓
③ Render:内存中算 diff(可中断 / 可重来)
        ↓
④ Commit:同步落地 DOM(不可中断)
```

### ① 触发更新与优先级分配(Lanes)

调用 setState / dispatch 或交互触发更新时,React **不会立刻改 DOM**,而是先启动调度:

- 创建 `Update` 对象记录更新内容,放入对应 Fiber 节点的 `updateQueue`;
- 按更新**来源**分配优先级(内部为 **Lanes** 位掩码模型):

| 来源                         | 优先级                    |
| ---------------------------- | ------------------------- |
| 离散交互(点击 / 输入 / 按键) | SyncLane(近似同步,最高)   |
| 连续交互(滚动 / 拖拽 / 悬停) | InputContinuousLane       |
| 网络请求返回的数据           | DefaultLane(普通)         |
| 后台预加载                   | IdleLane(最低,空闲时才做) |

### ② 任务调度与时间切片(Scheduler)

Scheduler 是独立于渲染逻辑的模块,接管更新任务并决定执行时机:

- 维护多个按过期时间排序的**最小堆队列**,高优先级任务排前、先处理;
- **时间切片**:把庞大渲染拆成小工作单元,借浏览器原生 `MessageChannel` 异步驱动;每处理约 5ms 就主动**让出主线程(Yield)**,检查是否有更高优先级任务插队,否则把剩余任务推迟到下一个空闲时间片继续。

### ③ 可中断的 Render 阶段

Render 只"算"不"改",任务是**计算差异**:

- 沿 Fiber 链表跑 Work Loop,基于新状态在内存中产出新的 `WorkInProgress` 树;
- 全程只做纯计算、不碰真实 DOM,因此**可中断**:若此时用户触发高优交互,React 会暂停低优渲染、甚至丢弃已算出的部分结果,优先处理高优任务,之后再恢复或重新开始;
- 遍历中对比新旧 Fiber 树(Diffing),为需要新增 / 修改 / 删除的节点打上**副作用标记(Flags)**,供 Commit 阶段使用。

### ④ 不可中断的 Commit 阶段

Render 算完即进入 Commit,任务是**执行更新**:

- **同步、一次性执行完**,防止用户看到渲染到一半、状态不一致的 UI;
- 按副作用标记集中批量修改真实 DOM;
- 随后处理副作用 Hook:`useLayoutEffect` 在浏览器绘制**前**同步执行,`useEffect` 在绘制**后**异步执行;
- **双缓冲切换指针**:把 Current 树与 WorkInProgress 树的引用交接,新 UI 正式上屏。

## 四、速查与总结

四个阶段各自干什么、能否被打断:

| 阶段          | 做什么                                              | 能否打断           |
| ------------- | --------------------------------------------------- | ------------------ |
| ① 触发 + 定级 | 建 Update 入队,按来源分配 Lanes 优先级              | —                  |
| ② Scheduler   | 最小堆排队,~5ms 时间切片,MessageChannel 异步驱动    | —                  |
| ③ Render      | 内存中遍历 Fiber 算出差量,产出 WorkInProgress、打标 | ✅ 可中断 / 可重来 |
| ④ Commit      | 同步落地 DOM,layoutEffect → 绘制 → useEffect,双缓冲 | ❌ 不可中断        |

**一句话总结**:Lanes 判轻重、Scheduler 排队切片、Fiber 在内存里可中断地"算"、Commit 同步不可中断地"落地"——四者配合,保证复杂应用在持续交互下仍高响应、不卡顿。回到开头:**闭包 + 链表给了函数组件"状态",Lanes + Fiber 给了它"流畅"**。
