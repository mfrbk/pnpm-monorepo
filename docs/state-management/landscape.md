# 坐标系与方法论:先分类,再解剖

> [← 返回总纲](./README.md) · 状态管理的"地图学":四类状态 / 五派库谱系 / 读懂任意状态库的解剖问题单

本系列总纲把"彻底了解状态管理"抽象成 **八个要点、两份源码答案**。动手深钻前,先立一张坐标系:**状态分几类、库分几派、以及读任何库时该逐条追问哪些问题**。坐标系立好了,后面每一篇都是在为同一张问题单填答案。

## 一、先给"状态"分类:四类,解法各不同

状态管理八成的纠结,源于把不同类型的状态塞进同一个 store。先按"谁拥有、活多久、是否要与外界同步"切开:

| 类别                       | 特征                                    | 典型例子                           | 适合的机制                                                                 |
| -------------------------- | --------------------------------------- | ---------------------------------- | -------------------------------------------------------------------------- |
| **本地 UI 态**             | 只服务单个/少量组件,可随组件卸载而丢弃  | 下拉开关、弹窗显隐、表单输入草稿   | 组件本地 `useState` / `ref`,或 React 的 `Context`                          |
| **全局客户端态**           | 多组件共享、跨路由存活、纯客户端逻辑    | 登录会话、主题、权限、国际化、布局 | **Store**(Zustand / Pinia / Redux)                                         |
| **服务端态(Server State)** | 来自远端,本质是"远端真实数据的本地缓存" | 接口返回的列表、详情               | **查询缓存**(TanStack Query / SWR),见 [Server State 篇](./server-state.md) |
| **URL 态**                 | 应可分享、可回退                        | 当前筛选、页码、搜索词             | URL(`useSearchParams` / `vue-router` query)                                |

**判断练习(选型前先自问)**:这份数据是**缓存**吗(远端是唯一真源、会失效、要被别人改写)→ 归服务端态;是我**自己**的业务全局吗 → 归 store;只是"这个组件自己开着没" → 就地 `useState`,连 store 都别进。把这三问刻进习惯,等于先用掉了状态管理一半的智慧。

## 二、给"库"定位:五派谱系

状态库不是一个品类,是几条被反复独立发明出来的路线。每派的核心是**对"状态如何变、变完如何通知 UI"的一个根本决定**:

| 派别                 | 一句话核心                                          | 代表                        | 最小思想样例                                                     |
| -------------------- | --------------------------------------------------- | --------------------------- | ---------------------------------------------------------------- |
| **Store / 集中仓库** | 状态收进一个显式仓库,读用 select、改走显式 API      | Redux、Zustand、Pinia、Vuex | `const store = { state, setState, subscribe }`                   |
| **原子 / 细粒度图**  | 状态是无数可组合的"原子",派生关系由依赖图自动推导   | Recoil、Jotai               | `const a = atom(0); const b = atom(get => get(a) * 2)`           |
| **可变 + 自动追踪**  | 状态就是普通可变对象,系统自动知道谁读了它、谁该更新 | MobX、Valtio                | `reactive({ count })` + 依赖追踪                                 |
| **状态机**           | 状态本身建模成"合法状态 × 合法转移",杜绝非法态      | XState                      | `{ initial:'idle', states:{ idle:{ on:{ FETCH:'loading' } } } }` |
| **查询缓存**         | 服务端数据当缓存管理:key / 过期 / 失效 / 去重       | TanStack Query、SWR         | `useQuery({ queryKey:['posts'], queryFn })`                      |

> 直觉:Redux 与 MobX 的分歧是"不可变 vs 可变"这一哲学问题;Recoil/Jotai 是想把"模块化 + 派生"做到极致;XState 是把"状态合法转移"显式化(相当于给布尔值的状态机);TanStack Query 干脆换个战场——承认远端数据是缓存。

## 三、为什么主角选 Zustand × Pinia(而非背一遍全家桶)

因为"彻底了解"的杠杆在**对照**,不在**清单**。Zustand 与 Pinia 是同一派(Store)内、同一代(把 Redux 的仪式砍掉后)的两个实现,**API 镜像般地像**(都有 `state / getter / action`,都鼓励多 store、模块化),内核却岔在整条路上最值钱的那一维——**变更如何传导到 UI**:

```
Zustand                      Pinia
──────────────────────────    ──────────────────────────
vanilla 内核,零框架依赖         深度绑定 Vue,store 就是 reactive 对象
自身实现"Set 订阅 + 全量通知"    骑在 Vue 依赖追踪上,"谁读谁被记录"
React 侧用 useSyncExternalStore Vue 侧天然精确到"读了哪个属性"
framework-agnostic 的"通用店"   为 Vue 而生的"活的对象"
```

看同一批要点时,这份差异就是最好的教材:**为什么 Zustand 需要 selector 来精准订阅?为什么 Pinia 的 getter 会自动缓存?为什么 Pinia 必须挂在 `app.use(pinia)` 上而 Zustand 不需要?** 每个"为什么"都通向一段机制切片——这正是本系列逐篇要挖的东西。

## 四、"读懂一个状态库"的解剖问题单

这是本系列贯穿全文的分析轴。拿到**任何**一个状态库的源码,按下面六问逐条作答,基本就把它读透了(前五问对应机制的"形",后一问对应"如何扩展与落地"):

### 问一 · 状态存哪?长什么样?

状态在内存里的容器是什么——单一对象树?多个扁平 store?无数原子?是普通对象、`reactive` 对象,还是不可变结构?**动机**:存储结构决定序列化、调试、时间旅行的成本。

### 问二 · 状态怎么变?谁有资格改?

更新入口有哪些——`set` 直接替换 / `dispatch(action)` 走 reducer / `$patch` 打补丁 / 直接改可变对象?是**替换**还是**就地修改**?**动机**:这决定了"改动的历史可不可追踪"与"变完如何对比新旧"。

### 问三 · 怎么"读"出可用数据?派生态由谁算?

读取形态是什么——选择器(selector)函数 / getter / computed?派生态是**每次现算**,还是**缓存 + 依赖失效**?选择结果**引用是否稳定**?**动机**:读得不准,UI 要么冗余重渲染、要么拿不到新值。

### 问四 · 变更如何传导到 UI?⭐ 分水岭

状态一变,靠什么让"依赖它的组件"重渲染——store 的**订阅-发布** + 框架桥,还是框架自带的**依赖追踪**?订阅的是**整树**还是**片段**?在**并发渲染**(React 可中断渲染)下怎么保证不错乱?**动机**:这是各库性能与心智负担差异的总根源,也最难。

### 问五 · 副作用与异步放哪?怎么防竞态?

请求、计时器、跨 store 编排写在哪——action 内部?中间件?独立进程?状态变更是**同步**还是可**异步**?乱序返回如何保证"过期的不覆盖新的"?**动机**:真实应用 90% 的诡异 bug 都在这。

### 问六 · 如何扩展?中间件 / 插件长在哪一环?

"在变更链上插眼"的机制是什么——Redux 的 middleware、Zustand 的中间件、Pinia 的插件?持久化、DevTools、undo/redo 是否第一等公民?**动机**:扩展点位置,决定了生态能力是内建还是后补。

把问题单合起来就是一句话——**存得清、改得稳、读得准、传得到、时序不乱、能扩展**。六问齐全,一个状态库在你眼里就透明了。
