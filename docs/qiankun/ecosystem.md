# qiankun 生态对比与选型(第 7 篇)

> [← 返回总纲](./README.md) · 本系列第 7 篇:方案谱系 / qiankun vs Module Federation / 无界 / micro-app / 到底要不要微前端 / 趋势

前六篇围绕 qiankun 本身把它讲透了。最后一篇把镜头拉远:**微前端方案谱系里 qiankun 站在哪、它的维护现状、以及——最该先问的那个问题——你的项目到底要不要上微前端。** 掌握这一篇,你才算"彻底了解微前端(qiankun)",而不只是会用 qiankun。

## 一、方案谱系:微前端怎么一步步走到今天

```
iframe 套壳(最原始)
   │  天然隔离强,但资源/会话/弹层/路由全要桥接,体验割裂
   ▼
single-spa(2015 前后)
   │  提出"生命周期 + 应用托管"模型 —— qiankun 借了这副骨架
   ▼
qiankun(蚂蚁,2019):HTML Entry + JS 沙箱 + 样式隔离 —— 把"应用级集成"做成了可落地的框架
   │
   ├─► 后起之秀(micro-app / 无界 / Garfish):同样解决"应用集成",换更强的隔离 / 更顺的接入
   │
   └─► 另一条线:Module Federation(webpack5,2020):不做"整应用",做"模块级共享"
```

两条主线的本质区别:

|            | 应用级集成(single-spa / qiankun / 无界 / micro-app) | 模块级共享(Module Federation)                  |
| ---------- | --------------------------------------------------- | ---------------------------------------------- |
| 拆分粒度   | 整块"页面级应用"(各自路由、各自发布)                | 模块 / 组件 / 依赖(可被任意远端动态 import)    |
| 代表性能力 | 生命周期托管、沙箱、路由插拔                        | `exposes/remotes/shared`,运行时共享 + 版本协商 |
| 典型诉求   | 多团队各管一个"系统"、独立发版                      | 跨应用复用组件与依赖、去重公共库               |
| 注意       | 页面组合问题(隔离 / 通信 / 弹层)                    | 无内置沙箱与路由,隔离靠规范,需自行组装         |

> **两者可叠加**:业界成熟组合正是"qiankun 管页面级集成 + Module Federation 管公共依赖共享"(如得物客服域的实践)。机制细节对照本仓库 [Webpack Module Federation 学习笔记](../webpack/module-federation.md)。

## 二、横向对比:qiankun vs 无界 vs micro-app vs Module Federation

一张表看主流方案现状(截至撰写时,以各家仓库/文档为准):

| 方案                  | 出品方       | 技术内核                            | JS 隔离                  | 样式隔离            | Vite 支持      | 路由                  | 维护状态                                  |
| --------------------- | ------------ | ----------------------------------- | ------------------------ | ------------------- | -------------- | --------------------- | ----------------------------------------- |
| **qiankun**           | 蚂蚁         | single-spa + HTML Entry             | Proxy/快照沙箱           | 可选(Shadow/scoped) | 差(需插件)     | 主应用路由驱动        | **实质停滞**(3.0 长期 rc,近两年无更新)    |
| **无界 wujie**        | 腾讯         | **iframe(可选)+ Web Component**     | iframe 原生(最强)        | 原生                | 好             | 子应用独立路由        | 活跃                                      |
| **micro-app**         | 京东         | Web Component(Custom Element)+ 沙箱 | JS 沙箱(类 qiankun 思路) | 支持                | **好**         | 主路由驱动+子路由同步 | 活跃                                      |
| **Module Federation** | webpack 官方 | 构建期无关的运行时模块共享          | **无内置沙箱**           | 无(需自管)          | 经 Vite 侧实现 | 无(需自组)            | 官方持续维护(@module-federation/enhanced) |

关键差异点的解释:

- **隔离天花板**:qiankun 的 Proxy 沙箱是"软隔离"(见[沙箱篇](./sandbox.md)),有逃逸与边界;**无界**用 iframe 承载 JS,拿到浏览器原生隔离,又通过桥接让 UI 融合与弹层接近原生;这是它对 qiankun 的主要卖点;
- **接入模型**:qiankun 要求子应用"UMD + 交生命周期"(存量 webpack 工程几乎零改造,但 Vite 难受);**micro-app** 用自定义元素当容器,对 Vite / ESM 更友好,接入更"元素化";
- **路由**:qiankun / micro-app 偏"主应用路由驱动、把子应用按前缀插进去";无界与 iframe 一致,子应用路由天然独立;
- **通信**:qiankun 用 props + Actions(见[通信篇](./communication.md));micro-app 提供 `window.microApp` 全局通信;无界依托同域 iframe 天然可通信;MF 则是"共享模块即共享状态"。

## 三、选型建议:什么情况用哪个

| 你的情况                                                        | 建议                                                                             |
| --------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| **存量 webpack 中后台整合**、团队要资料全、愿意接受方案停止迭代 | qiankun(成熟文档最多;留意 3.0 未发、更新停滞)                                    |
| **新项目 + Vite / 前端主技术栈现代**                            | **优先 micro-app / 无界**,或直接 Module Federation;别再为 qiankun 反向迁 webpack |
| 需求是"跨应用共享公共依赖 / 组件",发布仍可单体                  | **Module Federation**(webpack 系)/ Vite 生态的联邦实现                           |
| 要"最强 JS 隔离"、子应用含第三方不可控代码、保活 / 独立路由     | 无界(iframe 原生隔离)                                                            |
| 页面级整应用拆分 + 又想省公共依赖体积                           | **qiankun + MF shared** 叠加(或 micro-app 等对等组合)                            |
| 只是"把几个系统并排展示、无深交互"                              | 先质疑:iframe / 多 Tab 是不是就够了?微前端有成本,别为用而用(见下节)              |

## 四、先问一句:到底要不要微前端(和"康威定律")

微前端不是银弹,它的收益与代价都来自"拆"。**上之前先做收益审计**:

| 该上(强信号)                                          | 不该上 / 再想想(警惕信号)                                |
| ----------------------------------------------------- | -------------------------------------------------------- |
| 多个团队各自负责一块业务,**需要独立发布节奏**         | 单一小团队:模块化 + 代码分割 + 组件库就够                |
| 必须多技术栈并存 / 老系统渐进重构(不能停服迁移)       | 仅为"新鲜" / 面试写简历 → 成本远超收益                   |
| 单体应用构建/协作已到瓶颈(构建十几分钟、合并不停冲突) | 大但内聚:先试 monorepo + 独立包 + MF,未必需要页面级拆分  |
| 组织边界与系统边界一致(康威定律:架构追随组织)         | **组织还是一条线/一个 Owner → 拆出来的边界没人真正负责** |

**为"拆"付出的真实成本(三条,务必量化再拍板)**:

1. **隔离有边界**:软沙箱 + 样式方案的"挡不住清单"(见[沙箱篇](./sandbox.md)/[样式篇](./style-isolation.md))要求团队纪律:卸载清理、样式规范、弹层归位——每一条都是持续的约定成本;
2. **联调与发布变重**:跨应用联调、版本联动、灰度某子应用、错误归属——你从"单应用调试"进入"分布式调试";
3. **首屏与内存**:多应用资源重复、框架重复加载,首屏与内存要专门优化(见[工程篇](./migration.md))。

> 康威定律角度:**微前端最先要拆的不是代码,是团队与发布边界**。代码拆分是组织拆分的投影;反过来,组织没拆就硬拆代码,只会得到"伪微前端"。

## 五、趋势与"学 qiankun 还有没有价值"

- **维护现状要知情**:qiankun npm 主版本仍停在 2.x、3.0 长期 rc,社区普遍认为它已进入"存量维护"期;**选型时把它当"成熟的老方案"而不是"新项目的默认项"**;
- **技术趋势**:隔离在向"更原生"走(iframe/WebComponent/未来的 ShadowRealm 等标准能力),Vite/ESM 成为前端新默认,微前端方案的竞争点集中在"对 ESM 的友好度"与"隔离的真实强度";
- **但学 qiankun 不过时**:它的**生命周期模型、HTML-Entry 加载器、软沙箱思想、样式隔离边界**是理解一切微前端方案的通用底座——你读过的 single-spa 骨架在无界 / micro-app 里仍可辨认,边界问题(卸载清理、弹层、公共依赖)更是所有方案共通。**学完本系列,你学的不是"一个库",而是"一类架构问题"。**

## 速查

| 主题              | 一句话记住                                                                                     |
| ----------------- | ---------------------------------------------------------------------------------------------- |
| 两条主线          | 应用级集成(qiankun/无界/micro-app)vs 模块级共享(MF);粒度不同、可叠加                           |
| qiankun           | 成熟、文档全、HTML Entry + 软沙箱;但更新停滞,新项目慎选                                        |
| 无界 / micro-app  | 更现代的接入与 Vite 支持、更活跃;无界 iframe 原生隔离最强, micro-app 对 ESM 友好               |
| Module Federation | 共享模块/依赖,无沙箱无路由需自组;对照 [Webpack MF 文档](../webpack/module-federation.md)       |
| 要不要上          | 看组织/发布边界(康威定律);单团队、可模块化就先别上;成本 = 隔离纪律 + 联调发布 + 首屏内存       |
| 学什么            | 生命周期 / 加载器 / 沙箱边界是通用底座,迁移到任何方案都成立——学 qiankun 学的是"微前端问题本身" |
